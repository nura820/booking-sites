# Правила работы в этом репозитории

Сайты с онлайн-записью для малого бизнеса в Астане (QSA Studio): демо на три сферы, страница студии и сайты клиентов.

## Как устроено

- Next.js (App Router) со статической сборкой (`output: "export"`): сервера нет, сайт публикуется на GitHub Pages по адресу `/booking-sites/`. Перевод с одного файла `index.html` сделан по решению владельца 06.10.2026; прежняя версия лежит в `legacy/` для сверки и отката, её не править.
- Эта версия Next.js новее привычной: перед работой с его API читать нужную страницу в `node_modules/next/dist/docs/`.
- `src/data/niches.ts`: демо-данные трёх сфер. `src/data/clients.ts`: сайты клиентов, одна запись = страница `/c/<slug>/`. `src/data/studio.ts`: номер WhatsApp студии.
- `src/lib/booking.ts`: вся логика записи (окна, цены, длительность, маска телефона, текст заявки), чистые функции с тестами в `tests/`. Считать окна и суммы где-либо ещё нельзя.
- `src/components/site/site.tsx`: разметка и поведение сайта. `src/lib/motion.ts`: движение. `src/app/site.css`: оформление, цвета сфер через `body[data-n]`.
- Страницы: `/` (демо, вкладки), `/auto/`, `/coffee/`, `/barber/` (демо сразу в сфере; старые ссылки `?n=barber` переводятся сюда), `/c/<slug>/` (клиент), `/studio/`.
- Именной пример: `/barber/?b=<название>&a=<адрес>&t=<телефон>`. Только публичные данные бизнеса, не людей. Значения показываются как текст, до 60 знаков.

## Как мы делаем сайты (решение владельца 06.10.2026)

Работаем как «третий уровень»: не один промпт «сделай красивый сайт», а полный процесс.

1. Проектные инструкции ведём сами и держим актуальными: этот файл.
2. Перед кодом план: какие экраны, данные, состояния и тесты меняются.
3. GitHub: отдельная ветка на задачу, понятные коммиты, возможность отката.
4. Готовые библиотеки и компоненты вместо самописного, но в одной дизайн-системе: страницы не должны выглядеть собранными из разных проектов.
5. У каждого экрана есть состояния: загрузка, пусто, ошибка, успех, телефон.
6. Перед публикацией тесты и просмотр в браузере. Задача не готова, если страница только красиво выглядит: кнопки, формы и расчёты должны работать.
7. Настоящая публикация. Без лишнего усложнения: сервер, AWS, интеграции и приложение только когда они действительно нужны.

Образцы оформления владелец берёт на 21st.dev. Оттуда берём приём (кнопка с бликом, раскрытие заголовка по строкам, бегущая лента отзывов) и переносим на наш CSS и GSAP. Компонент целиком с его зависимостями (Tailwind, motion, shadcn) не подключаем без решения владельца; приёмы на canvas, WebGL и шейдерах не берём.

## Правила

- Библиотеки: Next.js, React, GSAP (с ScrollTrigger) и Lenis из npm. Новых не добавлять без решения владельца. Шрифты и фото лежат в `public/assets/`. Сайт не должен грузить ничего с чужих серверов, кроме запасных ссылок на фото.
- Язык интерфейса и комментариев: русский. Цены в тенге.
- Никакой графики, нарисованной кодом (canvas, 3D, декоративный SVG). Только фото и видео из `public/assets/` с запасными ссылками. Опубликованные пути `assets/...` и запасные ссылки не менять.
- Анимации появления 0,4–0,5 с. Содержимое должно быть в HTML страницы без JavaScript и видно при `prefers-reduced-motion`.
- Оплата: наличными на месте и Kaspi как необязательный вариант. Оплаты картой онлайн нет. Данные карт не собирать.
- Сайт не должен отправлять данные посетителей никуда, кроме явного действия пользователя (например, открытие WhatsApp с готовым текстом). Это проверяет тест в `e2e/site.spec.ts`.
- Не трогать крючки вёрстки: `data-tab`, `.tile`, `data-svc`, `#bnext`, `.slot`, `#fn`, `#fp`, `.okb`. На них стоят тесты.
- Оформление демо (шрифты, цвета-акценты, сетка) без задачи не менять: после любого изменения страницы трёх сфер сверяются со снимками до изменения.

## Порядок работы

- Каждая задача: отдельная ветка `task/<номер>-<кратко>`. Владелец разрешил (05.10.2026) вливать ветку в `main` самостоятельно, без запроса на слияние, но только после того, как прошли все проверки. Вливать обычным слиянием (`git merge --no-ff`), без `--force` и без переписывания истории `main`. Сайт публикуется из `main` (workflow `pages.yml`), поэтому в сообщении слияния и в отчёте писать: что сделано, как проверить, что не проверено. Если проверки не прошли, в `main` ничего не вливать: оставить ветку и открыть issue.
- Одна задача из `TASKS.md` за один запуск. Если задача неясна или требует решения владельца, не угадывать: открыть issue с вопросом и остановиться.
- Проверки перед слиянием в `main`:

      npm run typecheck && npm run lint && npm test && npm run build && npm run test:e2e

  и просмотр изменённого экрана в браузере на 390px и 1440px (`npm run preview`, адрес `http://localhost:4173/booking-sites/`).
